# dashrathkunwar.in

Welcome to the source code of my personal website — [dashrathkunwar.in](https://dashrathkunwar.in)

This site is:
- A living archive of my essays, ideas, and flânerie
- A digital playground for my experiments in aesthetics, coding, and autonomy
- A 2000s-style hacker den with dragons and Mishima references

## 🛠️ Built With

- HTML + CSS (no frameworks, no build step)
- Self-hosted fonts — no third-party requests, nothing phoning home
- Hosted on [GitHub Pages](https://pages.github.com/)
- Domain from [Hostinger](https://www.hostinger.in/)

## 🗂️ Structure

```

sw-register.js

img/                Banner artwork (WebP)
```

## 📥 Downloads

Everything below is generated by `tools/build.py`; none of it is committed by
hand.

| File | What it is |
|---|---|
| `writings/<slug>.pdf` | One PDF per essay, set in Crimson Pro, linked from the essay's share row |
| `downloads/writings.zip` | Every essay as HTML, plus `style.css` so they aren't raw text |

PDFs are built with `fpdf2` from the static fonts in `tools/fonts/` (fpdf2
can't read Google's variable originals, so those weights were instantiated
once with fontTools). Both the PDFs and the zip are written with a **fixed
timestamp** — with real mtimes the bytes would differ on every build and the
Action would push an empty commit each time.

**The essay zip is HTML only.** The PDFs stay on the site as individual
downloads; bundling them in as well roughly quadrupled the archive for no
gain (129 KB → 7 KB without them). The webfonts are left out for the same
reason — the CSS falls back to Georgia cleanly.

**There is deliberately no whole-site archive.** It was removed on purpose;
`build.py` deletes the file if an older build left one behind. Don't
reinstate it without asking.

## 📱 install.html

A standalone, step-by-step guide to adding the site to an Android or iPhone
home screen. It's linked only from the homepage footer, marked `noindex`, and
kept out of the nav, the feed and the sitemap.

## 📚 The catalogue

`books.html` is generated from `Library_Catalog.pdf` — 2,191 books across 34
collections. It is a catalogue of what's on the shelves, not a reading log and
not a list of recommendations.

Each collection is a `<details>` element with no `open` attribute, so they all
start **collapsed** and open on click — no JavaScript involved in the toggle
itself. Searching opens the collections that matched and clearing the box
collapses them again; jumping to `#some-collection` from the index expands it.

The entries are plain HTML, so the page works with JavaScript disabled;
`books-search.js` only filters what's already there. Search is case-insensitive
and accent-insensitive (`levi` finds `Lévi`), matches on title, author and
collection, and requires every word typed to appear somewhere in the entry.
Searches are shareable via `?q=`.

To add a book, add an `<li>` to the right `<section>`:

```html
<li><b>Author</b><cite>Title</cite><span>1943</span></li>
```

Drop the `<b>` if there's no author and the `<span>` if there's no year, then
bump the collection's count in the heading and in the collection index, and
bump `CACHE` in `sw.js`.

## 🌗 Themes

Dark is the default. The toggle in the top right switches to light and the
choice is remembered in `localStorage`.

Colours live in two blocks at the top of `style.css` — `:root` for dark and
`:root[data-theme='light']` for light. Everything else references the variables,
so adding a colour means editing those two blocks and nothing else.

Every page carries a small **inline, blocking** script in its `<head>` that
applies the saved theme before the first paint. Don't move it into `theme.js` —
deferred scripts run after paint, and a light-mode reader would get a black
flash on every page load.

Red and blue are darkened in light mode (`#c00000`, `#0057b8`): `#f00` and
`#0af` are fine on black but drop to ~4:1 and ~2.6:1 on white. Both palettes
clear WCAG AA on body text, headings, links and muted text.

## ✍️ Publishing an essay

Write Markdown in `posts/`, commit, done. Everything else builds itself.

```
posts/2026-07-27-some-essay.md
```

```markdown
---
title: The Weight of a Small Room
date: 2026-07-27
---

The first thing you notice about a small room is not its size but its
acoustics...
```

Commit and push. The GitHub Action runs `tools/build.py`, which:

- renders `writings/some-essay.html` from `tools/templates/post.html`
- adds the entry to `writings.html`
- adds the item to `feed.xml`
- adds the URL to `sitemap.xml`
- bumps the `sw.js` cache to a content hash

The site is live about thirty seconds later. You never touch the index, the
feed, the sitemap or the service worker by hand again.

Because it's just a file in a repo, you can write and publish from the GitHub
web editor (press `.` in the repo) or the mobile app — no local setup at all.

### Front matter

| Key | Required | Notes |
|---|---|---|
| `title` | yes | Used for `<h1>`, `<title>`, OG tags and the feed |
| `date` | yes | `YYYY-MM-DD`. Can come from the filename instead |
| `description` | no | Defaults to the opening line of the post |
| `slug` | no | Defaults to the filename after the date |
| `draft` | no | `true` keeps it out of the build entirely |

Name files `YYYY-MM-DD-slug.md` and `date`/`slug` are inferred — front matter
only needs `title`.

### Running it locally

```bash
pip install markdown
python tools/build.py --check
```

`--check` reports what would change without writing. `--drafts` includes posts
marked `draft: true`. The build is idempotent — running it twice changes
nothing the second time.

Deleting a Markdown file removes its generated page on the next build. Files in
`writings/` starting with `_` are left alone, which is how the mockup survives.

### The generated regions

`writings.html`, `feed.xml` and `sitemap.xml` are still hand-written files. The
build only rewrites what sits between the marker comments:

```html
<!-- BEGIN ENTRIES (generated by tools/build.py — do not edit by hand) -->
<!-- END ENTRIES -->
```

Edit freely outside them. Don't delete the markers — the build stops with an
error if it can't find them.

## 🔗 Sharing

Every essay gets a share row under the article, plus a toolbar that appears
when a reader selects a passage. Both live in `share.js`.

**Whole essay.** The "Post on X" link is a plain `<a>` with the URL already
baked in by the build, so it works with JavaScript disabled. "Copy link" and
"Share…" reveal themselves only if the browser can do them.

**A passage.** Select any text inside the article and a small toolbar offers:

| Button | What it does |
|---|---|
| Copy | The quote, the essay title, and a link straight to that passage |
| Copy link | Just the deep link |
| Post | Opens X with the quote and the deep link |
| Share | Native share sheet — mobile only |

The deep link uses a [text fragment](https://developer.mozilla.org/en-US/docs/Web/URI/Fragment/Text_fragments)
(`#:~:text=…`), so the recipient lands on the essay scrolled to that exact
passage with it highlighted. Supported in Chrome, Edge and Safari 16.4+;
everywhere else the link still opens the essay, just without the highlight.
The highlight colour is set by the `::target-text` rule in `style.css`.

### Instagram

There is no way to pre-fill an Instagram post or story from a web page —
Instagram publishes no share-intent URL, unlike X. A "Share to Instagram"
button on a website cannot work, so there isn't one here.

What does work: on a phone, "Share…" opens the operating system's share sheet,
and Instagram appears there alongside WhatsApp, Telegram and the rest. That is
the only real route, and it's the reason the native share button is worth
having. On desktop, Copy link and paste.

### The mockup

`writings/_mockup-essay.html` is a rendered specimen of every element
(headings, blockquote, lists, code, rules) in the site's styling. It's marked
`noindex`, nothing links to it, and the leading `_` keeps the build from
deleting it. Use it to check how a change to `style.css` affects essays.

## 🖼️ Artwork

Banners are WebP, sized to about twice their display height so they stay sharp
on high-DPI screens. If you add art, run it through the same treatment —
the originals were multi-megabyte PNGs being displayed at 400px.
